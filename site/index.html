Grisha is a command-line tool that makes a coding agent prove its work: a check that was run for every claim, and rules that keep banned lines out of new code.

  1. The agent writes a sheet

    You give your agent a task and say “use grisha”. It writes down what must be true when the work is finished, and the command that checks each claim.

    $ grisha start "Count only unread rows"
New sheet: ~/.grisha/repos/shop/tasks/count-only-unread-rows/sheet.json
Write the plan into it, then run `grisha next`.

  2. You approve it

    Your agent app shows you the plan and asks. Nothing is run before your yes, and any later change to the plan asks you again.

    $ grisha approve
The person approved the plan.
Next: counts-unread, still-a-number are not run. Run `grisha run counts-unread still-a-number`. A check for new behaviour has to fail before the change is made.

  3. The new check fails first

    Grisha runs the checks before any code changes. A check for new behaviour has to fail now, or it is not checking anything.

    $ grisha run counts-unread still-a-number
counts-unread: failed (exit 1)
…
still-a-number: passed
…
plan approved · 1 unit · 3 claims: 1 failing, 1 passes, never seen failing, 1 no check

  4. The agent makes the change

    The failing check passes now, so that claim is proven. The change touched code another check covers, so that one is out of date.

    $ grisha run counts-unread
counts-unread: passed
…
plan approved · 1 unit · 3 claims: 1 proven, 1 stale, 1 no check

Next: still-a-number is stale. Run `grisha run still-a-number`. Code it covers changed after it last passed.

  5. The gate stops the commit

    The agent tries to commit anyway. Your commit hook asks the gate, which refuses while a check is failing or out of date, or a rule is broken.

    $ grisha gate
Before this goes further:
- still-a-number is stale. Run `grisha run still-a-number`. Code it covers changed after it last passed.
(exit 1)

  6. A check has to be seen failing

    Run again, the stale check passes. It passed before the change too, so it has shown nothing. The agent breaks the code on purpose, watches the check fail, and restores the code.

    $ grisha run still-a-number
still-a-number: passed
…
Next: still-a-number passes but was never seen failing. Break the code it covers, run `grisha run still-a-number`, restore the code and run it again.
…
$ grisha run still-a-number
still-a-number: failed (exit 1)
…
$ grisha run still-a-number
still-a-number: passed
…
plan approved · 1 unit · 3 claims: 2 proven, 1 no check

  7. A rule blocks a line the agent added

    A rule is a pattern that lines of code may not match: a comment, a skipped test, a mock. It blocks what a branch adds and only counts what was already there, so you can turn one on in an old codebase today.

    $ grisha rules
src/billing.ts:1  no-comments
  + // TODO: bill unread rows only
…
Each rule, the lines it blocks, and the lines already in the code that match it:
  no-comments             added lines  1 line in 1 file

  8. Nothing is left

    No command can settle the last claim, so the agent leaves it for you to read. Every claim with a check is proven and no rule is broken.

    $ grisha next
Count only unread rows
plan approved · 1 unit · 3 claims: 2 proven, 1 for you to read

Nothing is left: every claim with a check is proven and no rule is broken. `grisha pr` prints the proof for the pull request.
Left for the person to read: other-tenants, another tenant's rows never count.

  9. The proof goes in the pull request

    Every claim, the command that checked it and where it stands, with what is left for you to read.

    $ grisha pr

Try it on your own code

Grisha runs on Bun. The rules work as soon as they are written, with no agent and no task. The rest starts when you tell your agent to “use grisha”.

  1. $ npm install -g @brianmeier/grisha
  2. $ grisha rules --init
  3. $ grisha rules
